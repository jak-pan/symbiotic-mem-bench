# Membench v2.0.0 release candidate

Status: **prepared, not tagged or released**.

## Reviewed source boundary

- Release-readiness base: merged master
  `61eb0bc935dd810aaa857f529fc8fcfc474525d0` (authentic v2 cockpit, PR #10).
- Release-readiness changes: issue #11 and its eventual exact merged commit.
- Product UI v2 means the server-backed operator interface. It is not an official
  LongMemEval-V2 scoring claim; `longmemeval-v2-text` remains experimental and unranked.

## Intended public assets

- `membench-v2.0.0-x86_64-unknown-linux-gnu.tar.gz`
- `membench-v2.0.0-aarch64-apple-darwin.tar.gz`
- one `.provenance.json` and one `.tar.gz.sha256` beside each archive
- aggregate `SHA256SUMS`
- GitHub-generated source `.tar.gz` and `.zip`

Each product archive contains only the read-only public product: `membench-server`,
`membench-leaderboard`, `dashboard/dist/`, portable tracked `records/`, legal/security/release docs,
and `PROVENANCE.json`. It excludes the private Symbiotic Memory adapter, private source, zvec native
packages, credentials, local runs, raw provider payloads, raw/vault/workflow/provider-queue state,
and SQLite files.

## External/private integration boundary

`symbiotic-sh/symbiotic-memory` is still private. Maintainers must pass the exact-pin adapter gate
before tagging, but that credentialed build is compatibility evidence only. The public default,
server feature, source checkout, and attached product bundle must build/install and run without
access to that repository. The adapter can become a public asset only after its complete source and
native zvec runtime are publicly reproducible for the claimed target.

## Exact tag checklist

1. Merge issue #11 only after exact-head review and all hosted CI checks are green.
2. From a fresh clone at that merge commit, run every pre-tag command in `RELEASING.md`, including
   the private adapter compatibility gate on an authorized maintainer machine.
3. Build the local platform package twice from identical inputs and epoch; require identical archive
   SHA-256. Unpack it outside the checkout and verify health, runs, ranked leaderboard, 500 Questions,
   and Traces.
4. Confirm `git status --short` is empty and `v2.0.0` does not already exist locally or remotely.
5. Create one annotated `v2.0.0` tag pointing to the reviewed merge commit and push only that tag.
6. Let `.github/workflows/release.yml` rerun gates and create the draft release. Do not publish if
   either target, checksum, provenance document, or extracted-bundle smoke is missing.
7. Download the draft assets, verify `SHA256SUMS`, repeat one server-backed smoke, and deploy a canary
   from that downloaded asset.
8. Publish the GitHub release only after the canary reports the tag commit, server binary hash, UI
   bundle hash, and records digest from its `PROVENANCE.json`.

No step above has authorization to create the tag or release as part of the release-readiness PR.
